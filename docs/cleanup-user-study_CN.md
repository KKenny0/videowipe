# 真实用户试用与可用结果成本记录

本流程用于 [#14](https://github.com/KKenny0/videowipe/issues/14) 和 [#15](https://github.com/KKenny0/videowipe/issues/15)。目前尚无五位真实参与者的试用记录，历史案例的真人修改、审阅时间及可用结果总耗时也未测。本页和空模板只用于准备，不代表验收完成。

## 开始条件

项目负责人提供五位真实参与者及获准使用的素材。每人使用匿名编号；原片、联系方式和授权凭据留在本地。没有另行授权，不将素材或可识别信息上传 GitHub。记录素材的使用许可与公开许可，两者分开。

固定产品提交、安装包及设备。按[工作台说明](cleanup-workspace_CN.md)启动已有网页；不为试用增加开发版能力。为每次试用复制一份[空记录模板](cleanup-user-study.template.json)，将 `record_kind` 改为 `observation`。缺失字段保留 `null`；零秒、零次必须有真实观察依据。

材料至少记录原片 SHA-256、时长、尺寸、实际解码帧数，以及用户希望删除和保留的内容。计划、试擦、最终输出分别保存身份与关联的任务／审阅版本。私人路径只留在本地记录，公开汇总使用匿名编号和哈希。

## 一次试用

每位参与者使用同一开场说明：“请用这条素材完成你刚才说明的删除与保留目标。先看默认结果，再决定是否修改。你可自行查阅公开说明。最后判断完整输出是否愿意使用，也可以停止。”这里的“独立”指读过这份统一任务说明后没有额外操作帮助；观察者不要补充具体按钮、框选或参数提示。

1. 用户先说明目标，再从选择素材开始操作。观察者提供按钮路径、选框、参数或故障恢复提示时，记为人工协助，保留发生时点及具体内容。
2. 先走默认路径，保存零编辑的候选、计划、推荐试擦与完整输出。不要提前替用户改目标。记录第一次看到试擦的时点及该次运行的机器阶段记录。
3. 用户不接受时，可用已有的选择、框、时间和保护编辑继续处理。分别记录保存请求、实际配置变化、修改轮次及导出尝试：相同配置重发或请求重试不算新的配置变化；用户完成一组修改后提交试擦算一轮，多个自动保存不算多轮；同决定重新导出只增加导出尝试。保留前后配置身份、计划及失败产物。历史“一次逻辑修改、两次导出”沿原记录口径保留，不直接当作采用这些前瞻定义采集的数据。
4. 用户以正常速度检查输出，分别判断目标是否去净、非目标是否保留、是否有闪字／残影，以及是否愿意使用。记录完整观看与否、问题位置和原话。导出完成、抽帧通过和用户接受分开；发现失败不需要强迫看完才承认失败。
5. 记录最终为 `first_pass_success`（默认零编辑的完整输出获用户接受）、`corrected_success`（实际修改后完整输出获接受）、`failed`（本次已结束且结果不合格）或 `abandoned`（用户主动放弃本次目标）；`pending` 只用于仍在进行或尚未判断的会话。试擦接受不能替代完整输出接受。失败或放弃均记录观察截止与已花费时长，可用结果总耗时保持 `null`。同时记录独立完成／人工协助、失败或放弃原因，以及是否愿意再处理第二条素材。询问使用意愿，不把回答当作实际复用行为。
6. 用户作出判断后，再由内部审阅者记录技术判断和双方差异。若用户接受但固定保护区像素检查失败，两项均保留；内部判断不能覆盖用户原话，用户接受也不能抹掉工程失败。

不预设所有人都需要修改，也不制造失败来填表。五人不足时，#14 保持未完成。只报告实际人数、过程与原话，不将五人的比例推广为总体成功率。

## 时间与运行条件

使用同一观察时钟记录带时区的时间，或用计时器直接测量区间。不要用返回文件的时间戳倒推真人操作时间。产品现有 `benchmark.json`、任务状态、HTTP 原始记录和缓存回执继续作为机器计时来源，不另造一套性能计时器。

| 字段 | 起止与解释 |
| --- | --- |
| 会话起点 | 用户开始选择本次素材；另存服务接收上传的时点，避免混淆用户等待与服务器耗时 |
| 首次效果等待 | 会话起点到第一次可播放试擦；同时保留已有机器记录的计时起点与范围 |
| 人工设置／编辑／审阅 | 记录各段实际活动的起止、动作与记录人；HTTP PATCH 延迟不是编辑时间 |
| 再处理与完整导出 | 每次运行分别保存机器阶段、重试原因及产物，不能只保留最快成功一次 |
| 可用结果总耗时 | 会话起点到用户明确接受指定完整输出；未接受时为 `null` |
| 失败或放弃耗时 | 会话起点到停止，单列；不计为得到可用结果 |
| 暂停或外部中断 | 原样记录，不默认从总耗时扣除；如另报净时长，必须说明扣除了哪些区间 |

人工活动、等待与机器运行可能重叠，不直接将它们相加当作总耗时。总耗时取真实起止，分项用于解释。故障诊断、实验检查器中断及生成对比文件等观察工具开销单列，不当作产品固有成本。

每次运行单独记录以下条件，未知就填未知：

- 进程是新建还是复用，模型在本次请求前是否已经加载，是否包含权重下载。
- 设备、系统、Python、后端、精度、权重 SHA-256、检测预设、OCR、修复参数、输入及产品版本。
- 试擦缓存是否命中、预测缓存的命中／未命中计数及回执来源。缓存目录存在不等于命中。
- 同期是否有其他计算任务，以及 OS／文件缓存是否测量。新进程不自动等于严格冷启动。

正式性能比较按顺序运行，避免模型、检测或编码任务争用资源。将冷启动、模型已加载的热运行、经回执确认的缓存命中分组；不要强行将历史未知记录放入其中。

## 汇总与结项

每人至少一行，包含匿名编号、目标、默认结果、修改次数、最终结果、独立／协助、放弃原因、第二条素材意愿、时间缺项及原始记录位置。机器耗时可在未完成会话中报告，但“可用结果成本”必须关联用户已接受的指定输出。

#15 同时展示默认成功、修改后成功和失败案例。旧英文／多语接受、中文失败及一次框修改接受可以沿原身份复用；历史未测的真人时间保持未知，不要求用户重新签收来补造计时。新前瞻观察才能补齐真人操作与审阅时间。

报告最值得缩短的环节时，先比较真实等待、反复修改、重试和审阅。只有原始记录支持时才量化节省空间；阶段最慢不自动等于用户最痛，也不在本票夹带性能优化。资料不足时说明缺口和下一次测量条件，票据保持开放。
